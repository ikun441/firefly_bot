## 一、数据隔离：测试数据污染生产库

### 1.1 症状

`app.debug=false` 时，总览页与报告页仍显示 **1299 元**支出 —— 与真实账目无关的历史数字。

### 根因

测试脚本写入的流水残留在正式库中，且**回收机制没跑起来**：以
`python tests/test_api.py` 方式运行时项目根不在 `sys.path`，`import firefly`
全线 ImportError，基线快照失败被静默忽略。

### 修法

- 修正测试入口的模块路径，保证 `import firefly` 可用；
- 为同批入库的流水补登记回收名单，测试结束统一清理。

### 1.2 症状

报告页仍残留 2598 元等历史数字。

### 根因

报告归档 `ff_report` 未随测试清理，`/api/reports/latest` 仍返回**旧报告 payload** ——
而 payload 是报告页与推送图片的唯一真值来源。

### 修法

- 测试回收扩展到报告与税务检查表；
- 清空已归档的历史报告，使前端重新生成。

> **核心教训**：测试回收不能只依赖「测试跑完自己清理」—— 一旦测试因 import
> 失败而中断，清理逻辑根本不会执行，而失败信息又被 `try/except` 吞掉。
> **静默失败比报错危险**。

## 二、金额字段缺上界 → 浮点精度漂移

### 症状

`POST /api/transactions` 提交 `999999999999999` 直接入库，总览页显示天文数字，
且回读值已从 `999999999999999` **漂移**成 `1000000000000087`。

### 根因

所有金额字段只写了 `gt=0`，没有上界。SQLite 用 IEEE754 双精度存储 REAL，
超过 2^53 后整数不再精确。该值还会被 `/api/stats` 收支合计、报告 payload、
预算进度一并吸收，用户很难定位是哪一笔。

### 修法

在 `deps.py` 定义 `MAX_AMOUNT = 1e8` 作为**唯一来源**，统一应用到
交易、AI 确认、账户期初、预算、订阅五处。

**关键细节**：修复时不能简单给所有字段加 `gt=0`。项目约定
**「业务规则错误走 HTTP 200 + `success:false`，只有字段校验错误才返回 422」**，
而预算/订阅的负数原本由 service 层拦截并返回带文案的信封。若把它提到
pydantic，会变成裸 422（没有 `success` 字段），前端拿不到提示。
最终**只卡上界、不动下界**：

| 场景 | 修复后响应 |
| --- | --- |
| 预算 / 订阅负数 | 200 + `{success:false, message, code}` |
| 金额超 1 亿 | 422 |
| AI 批量确认含负数 | 200，跳过该条，其余正常落库 |
| 交易负数 | 422（`gt=0` 原本就在 schema 中） |

## 三、前端账本选择失效（3 个子问题）

### 3.1 手动记账「关联账本」显示暂无可用账本

- **根因**：`collector.js` 写成 `window.FFApi.accountsList()`，而该方法挂在
  内层 `api` 对象上；调用即抛 `TypeError`，被外层 `catch` **静默吞掉**，
  `/api/accounts` 请求从未发出。
- **修法**：改用已声明的 `api.accountsList()`；并让 `window.FFApi` 展开内层
  方法，两种写法都可用。

### 3.2 自然语言记账识别后没有账本选项

- **根因**：前端确认区压根没有该字段；后端 `NLItemIn` 也不存在 `account_id`，
  即使传了也会被 pydantic 丢弃，落库时 `account_id` 恒为 `None` ——
  流水永远不进任何账户余额。
- **修法**：前后端同时补：前端加下拉，后端加字段并接进 `create_transaction`。

### 3.3 点击「确认入账」恒返回 422，功能实际不可用

- **根因**：LLM 抽出的类别名匹配不到已有类别时，前端传 `category_id: ""`，
  过不了 pydantic 的整数解析。
- **修法**：前端空串转 `null`；后端放宽为 `Union[int, str]` 并用 `_as_int()` 归一化。

> **第 3 条的隐蔽点**：`item.category_id in id_set` 中集合元素是 `int`，
> 而前端 `<select>` 的 value 永远是字符串，不做归一化则**永远匹配不上**，
> 用户的类别选择会被静默丢弃、全部记成未分类。这类「字符串 vs 整数」的坑
> 统一用 `toId()` / `_as_int()` 在入口处收口。

## 四、静默失败的治理

上述多个 bug 的共同特征是：**异常被 `catch` 吞掉，表现成「什么都没发生」** ——
页面不报错、请求不发出、数据静默丢失，排查成本极高。

治理方式：

- `window.FFApi` 展开内层方法，消除「两种写法、一种必错」的陷阱；
- 静态资源走 `NoCacheStaticFiles`（`Cache-Control: no-cache, must-revalidate`），
  避免浏览器拿旧 JS 复现已修好的 bug。

> 部署后**务必强制刷新（Cmd+Shift+R）**，否则可能仍在跑旧的 JS 缓存。

## 五、`POST /api/tax-check` 返回 500（周期常量漏 import）

### 症状

税务自检接口直接 500。

### 根因

合法周期集合原先在 `report.py` / `stats.py` 各写了一份，而 `taxcheck.py`
想用时**漏了 import**。常量散落多处时，「少写一个 import」的代价就是
整条链路不可用。

### 修法

在 `firefly/api/deps.py` 定义 `VALID_PERIODS` frozenset 作为**唯一来源**，
各路由统一引用；同时周期是用户输入，在路由入口显式校验，
非法值返回 200 + `success:false`（业务错误）而非 500。

## 六、`/api/settings` 嵌套写法绕过白名单（安全漏洞）

### 症状

早期只在「扁平写法」（`{"auth.secret_key": "x"}`）分支上做白名单校验，
而「嵌套写法」（`{"auth": {"secret_key": "x"}}`）会绕过检查直接写入 ——
实测可以把 `secret_key` 覆盖成攻击者指定的值，从而**伪造任意登录令牌**。

### 修法

让校验覆盖**所有输入语法形态**（扁平点号键与嵌套对象都校验）；
`password_hash` / `password_salt` / `secret_key` 列入
`SYSTEM_MANAGED_FIELDS`，API 永远拒绝写入。

> **教训**：白名单漏一种写法，就等于没有白名单。

## 七、CSV 导入 `dry_run` 查询参数被静默忽略

### 症状

`?dry_run=true` 放在查询串里时**不生效**，接口照常执行真实入库，
返回的还是普通的导入结果 —— 调用方以为自己在预览，实际已经写库了。

### 根因

`dry_run` 原先只写成 `Form(default=False)`，只有 multipart 表单字段能触发预览。

### 修法

同时声明 `Query` 与 `Form`（`dry_run_form`，alias=`dry_run`）：
表单字段显式传了就听它的，查询参数兜底（curl / 脚本的直觉用法）。

## 八、备份还原路径穿越防护

### 风险点

`GET /api/backup/download?name=../../../etc/passwd`。

### 修法

`Path(name).name` 剥掉任何目录部分，`../../../etc/passwd` 变成 `passwd`，
随后在备份目录里找不到 —— 路径穿越到此为止。文件不存在时返回
200 + `success:false` 信封，与全项目约定一致。

## 九、演示模式失效（`/api/bootstrap` 拆分）

### 症状

配置里开着 `app.debug`（演示模式），但页面仍去打真实接口，演示模式完全失效。

### 根因

早期让前端用 `/api/meta` 来设置 debug 开关，而该接口**受鉴权保护**，
未登录时返回 401，于是 `debug` 永远没被设上。

### 修法

把「纯展示配置」拆成独立的 **`GET /api/bootstrap`**（免登录，刻意不含
用户、税率、推送目标等任何业务字段）；`/api/meta` 保持受保护，
登录后才返回业务信息。

## 十、Console 适配器刷掉启动横幅

### 症状

启动后终端被 ANSI 转义码刷屏，看不到访问地址。

### 根因

Console 适配器是交互式 TUI，会接管整个终端。

### 修法

默认**不注册** Console 适配器；仅在有真实 TTY 且显式设置
`FIREFLY_ENABLE_CONSOLE_BOT=1` 时才加载。

## 十一、一键启动脚本的三个问题

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 明明装了 Python 3.11，脚本却报「版本过低」 | conda 的 python 不在 PATH 里，只按 `python3.xx` 命令名探测会漏掉 | 回退扫描 `~/miniforge3`、`~/miniconda3` 等常见前缀及其 `envs/*` 子环境 |
| 2 | 脚本选中了 Python 3.14，装完依赖起不来 | 版本判断只设了下界，而 miniforge base 往往是 3.13/3.14，从高到低找会先命中它 | 加**上界** 3.12，检索顺序改为 `3.11 → 3.12 → 3.10` |
| 3 | **项目源码目录被整个覆盖** | 虚拟环境命名为 `firefly`，与 Python 包目录 `./firefly/` 路径完全相同，`python -m venv` 直接写入同一路径 | 改名 `firefly_env`，并在脚本启动前加同名冲突检测 |

**第 3 条最值得记录**：它的报错是 `No module named firefly.app`，
完全指向不了「命名冲突」这个真实原因，排查成本极高。
好在源码已提交进 git，用 `git checkout -- firefly/` 完整恢复（52 个文件校验一致）。

### 附带修复

`.env` 里残留未注释的空 `SUPERUSERS=` 会导致 NoneBot 启动早期抛
`SettingsError: error parsing env var "superusers"`，服务刚起就退出 ——
脚本启动前会自动把它注释掉。
